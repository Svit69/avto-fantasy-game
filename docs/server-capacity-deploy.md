# Включение на VPS

1. Обновите код и зависимости: `git pull`, `npm ci`, `npm run check`.
2. В существующий `.env` добавьте `OPERATIONS_MONITOR_TOKEN` и `TELEGRAM_WEBHOOK_SECRET`: два разных случайных значения, например результат двух запусков `openssl rand -hex 32`.
3. За Nginx задайте `HOST=127.0.0.1`. `TRUST_PROXY=true` включайте только если прямой доступ к Node закрыт и Nginx перезаписывает X-Forwarded-For.
4. Не включайте лимит задержки: оставьте `MONITOR_API_P95_WARN_MS=0`.
5. Проверьте `pm2 list`: если есть старый отдельно созданный `avto-vhl-online-poll`, сначала остановите его по точному имени из списка.
6. Примените конфигурацию: `pm2 startOrRestart ecosystem.config.cjs --update-env`, затем `pm2 save`.

Старый и новый `avto-fantasy-vhl-poll` не должны работать одновременно. Не удаляйте основной процесс приложения.
Пул основного процесса по умолчанию 4, в ecosystem у ВХЛ 2. Другие CLI-процессы также создают собственный пул; не запускайте массовые импорты параллельно без необходимости.

## Однократная настройка webhook

После рестарта сразу зарегистрируйте webhook с секретом, не удаляя ожидающие обновления:

```bash
curl -X POST https://ВАШ-ДОМЕН/api/telegram-set-webhook \
  -H 'Authorization: Bearer ВАШ_OPERATIONS_MONITOR_TOKEN'
```

Замените значения на свои, не публикуйте токены и не оставляйте их в общедоступных логах.
С этого момента входящие webhook проверяются по секретному заголовку Telegram. Пока секрет не задан, сохранён режим совместимости и выдаётся предупреждение в логе; аутентификации webhook нет.
Без `OPERATIONS_MONITOR_TOKEN` установка webhook, `/api/operations`, `/api/telegram-bot-info` и `/api/telegram-webhook-info` запрещены. Диагностика Telegram требует тот же Bearer-токен.
Проверьте `/api/health`, `/api/ready`, обновление heartbeat ВХЛ и обычный сценарий сохранения состава.

## Nginx и память

Примеры в `deploy/nginx-capacity-http.conf` и `deploy/nginx-capacity-locations.conf`. Не вставляйте второй блок рядом с уже существующими такими же location: объедините конфигурацию.
Ограничение Nginx сначала работает в dry-run. После анализа логов можно включить фактическое ограничение. Сначала `nginx -t`, затем reload.
Для PM2 под root есть `deploy/logrotate-avto-fantasy.conf`: установите в `/etc/logrotate.d/avto-fantasy`, проверьте `logrotate -d /etc/logrotate.d/avto-fantasy`. Для другого пользователя исправьте пути и `su`.
Проверяйте частоту запуска logrotate: `maxsize` проверяется при запуске, это не мгновенный предел. Ротация Nginx обычно настроена пакетами ОС, её тоже проверьте.
После замеров RSS можно передать `APP_MAX_MEMORY_RESTART` и `VHL_MAX_MEMORY_RESTART` в окружение команды запуска PM2, либо задать `max_memory_restart` в ecosystem.
Это страховка, не мгновенный предел памяти; не подбирайте значения по проценту Node heap и не задавайте их близко к обычному RSS.

## Внешний монитор

Запустите `server/health-probe.js` на ДРУГОЙ машине раз в минуту. Проверка на том же VPS не обнаружит его полное отключение.
На внешней машине нужны Node.js, проект с зависимостями и отдельный `.env` только с `HEALTH_PROBE_URL=https://ВАШ-ДОМЕН/api/ready`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_IDS`.
Не копируйте на монитор пароль PostgreSQL или весь production `.env`. Состояние монитора хранится локально между запусками.
Пример cron (не запускайте два экземпляра одновременно):

```cron
* * * * * cd /opt/avto-monitor && flock -n /tmp/avto-health-probe.lock /usr/bin/node server/health-probe.js >> /var/log/avto-health-probe.log 2>&1
```

Предупреждение — после трёх неудачных проверок подряд с таймаутом 10 секунд, восстановление — после двух успешных. Повторы не чаще 15 минут.
Такое сообщение означает недоступность из внешней точки: причиной может быть и сеть монитора. Проверяйте метрики и логи прежде чем перезапускать сервер.
