# Защита VPS от перегрузки

## Что включено

- Обычные чтения API: 8 выполняющихся + 32 ожидающих; записи: 2 + 8. Webhook отдельно: максимум 4 HTTP-запроса, обработка 2 + очередь 8.
- Частота по проверенному пользователю: чтение 180/мин, запись 30/мин, всплеск 20. Анонимные запросы имеют более мягкие IP-лимиты для общих сетей.
- При переполнении возвращаются 429/503 и `Retry-After`; память очередей и таблиц лимитов ограничена.
- Чтения и проверка авторизации повторяются клиентом максимум дважды только после 429/503, с паузой и случайным сдвигом. Сетевые ошибки не вызывают такой повтор.
- Запись состава не повторяется автоматически. При отказе выбор остаётся на экране, кнопка снова доступна.
- Импорт и расчёт цен используют одну межпроцессную блокировку `proper-lockfile` и очередь 4. Все процессы должны использовать одну директорию `RUNTIME_STATE_DIRECTORY`.
- Кеш цен: 90 секунд, объединение одновременных расчётов; импорт, цена и команда обновляют общую ревизию. «Пересчитать» обновляет кеш принудительно.
- Цикл ВХЛ не пересекается со следующим; heartbeat хранит завершение цикла и ошибки отдельных матчей.
- Обычное тело HTTP: 64 КБ, ручной импорт: 8 МБ; скачиваемый протокол: 8 МБ, 60 секунд. Статика передаётся потоком.
- PostgreSQL: пул 4 по умолчанию; PM2 для ВХЛ задаёт 2. Ожидание соединения 3 секунды, SQL statement timeout 30 секунд.

## Задержки и мониторинг

`MONITOR_API_P95_WARN_MS=0` по умолчанию: предупреждение по задержке отключено.
При включении измеряется только обычный GET: от принятия сервером до вызова `response.end`, включая внутреннюю очередь и работу, но не отправку ответа в сеть.
Webhook, обращения к Telegram и загрузка POST-тела исключены. Нужны минимум 50 запросов за 5 минут и превышение в течение 3 минут.
Эта метрика никогда не ограничивает запросы, не отменяет операции и не перезапускает процесс. Можно начать с 5000 мс после наблюдения.
Монитор проверяет ресурсы каждые 15 секунд: `MemAvailable` <100 МБ 3 минуты, <50 МБ 30 секунд, CPU >85% 5 минут, диск <15% 2 минуты, swap >100 страниц/сек 2 минуты.
Также контролируются event loop, 5xx, PostgreSQL, ожидание пула и ВХЛ. Таймаут heartbeat: максимум из 10 минут и трёх интервалов опроса.
Ошибки ВХЛ вызывают тревогу после трёх неуспешных циклов подряд; одиночные сбои остаются в логах. Успешный цикл сбрасывает счётчик. Для старого heartbeat без счётчика действует порог пять минут.
Уведомления отправляются `TELEGRAM_ADMIN_IDS`, повторы не чаще 15 минут; восстановление — после минуты нормы. Ошибки доставки повторяются не чаще минуты.

## Проверка состояния

- `/api/health`: жив ли HTTP-процесс, без проверки БД.
- `/api/ready`: готова ли БД; проверка объединяется и кешируется на 3 секунды. Для JSON БД помечается `not_configured`.
- `/api/operations`: подробные метрики, доступ только с `Authorization: Bearer OPERATIONS_MONITOR_TOKEN`.

Нельзя гарантировать предупреждение до мгновенного OOM или выключения VPS. Для этого нужен внешний монитор: см. `docs/server-capacity-deploy.md`.
Монитор не меняет лимиты автоматически и не завершает процессы. PM2-пороги памяти намеренно не заданы без измерения пиков импорта.
Блокировка тяжёлых задач имеет heartbeat, stale=10 минут. При аварийной потере lock библиотека прекращает процесс; после обычной ошибки задачи lock освобождается.
Не удаляйте активный lock вручную; пути и параметры lock должны совпадать во всех процессах. На разных VPS этот механизм требует общей файловой системы или замены на распределённую блокировку.
Webhook-квитанции переживают перезапуск; хранятся примерно до 2000 записей/24 часов с периодической очисткой. Подтверждение HTTP выполняется после обработки и записи квитанции.
Повтор завершённого update не повторяет изменение данных, но может повторить ответ бота. Авария между побочным действием и записью квитанции не обеспечивает exactly-once; длительные диалоги остаются в памяти.
Используется один HTTP-процесс PM2, не cluster. Внешний монитор и воркер — отдельные процессы.
Для JSON-хранилища устанавливайте `API_WRITE_CONCURRENCY=1`; для рабочего VPS рекомендуется PostgreSQL.
Проверки: `npm run check`, отдельно `npm run test:operations`. Нагрузочные тесты выполняются на локальном временном сервере, не на production.
