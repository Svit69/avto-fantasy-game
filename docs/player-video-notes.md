# Кружки хоккеистов

## Администратор

1. `/admin` → «База хоккеистов» → команда → позиция → игрок → «Кружок игрока».
2. «Загрузить / заменить кружок» → следующим сообщением отправить кружок Telegram или переслать его из канала.
3. Обычные видео и файлы не преобразуются в кружки. При неверном сообщении бот продолжает ждать кружок; отмена доступна кнопкой.
4. `/admin` → «Кружки хоккеистов»: список записей, просмотр, замена, удаление с подтверждением.
5. «Игрок покинул команду» с подтверждением использует существующий уход из игры: игрок недоступен для выбора и рассылки. Запись сохраняется для администратора.
6. «Тест по моему составу» → тур: один кружок из собственного сохранённого состава из шести разных игроков, даже до дедлайна. Остальным ничего не отправляется; журнал рассылки не меняется.
7. Просмотр отдельной записи доступен и без собранного состава.

## Автоматическая отправка

- Кружки приходят в личный чат пользователя с ботом, не публикуются автоматически в канале.
- Один кружок на пользователя за тур. Выбирается один из активных хоккеистов его сохранённого состава с записью; выбор стабилен между перезапусками.
- В составе должно быть шесть разных игроков; пользователь должен быть активен. Без подходящего кружка отправки нет.
- Учитываются записи, загруженные до дедлайна, и составы, сохранённые не позже него. Новые записи не вызывают рассылку за старые туры.
- Планировщик встроен в HTTP-сервер: проверяет очередь раз в минуту. После простоя догоняет отправки в течение 24 часов после дедлайна.
- Существующий `npm run notify:draft` тоже поддерживает кружки; общая межпроцессная блокировка защищает от одновременной обработки с планировщиком.
- Ограничения скорости и размера пакета общие с другими рассылками: `NOTIFICATION_RATE_LIMIT_PER_SECOND`, `NOTIFICATION_BATCH_SIZE`.
- Telegram хранит сами видео; повторная отправка использует `file_id` ([Bot API](https://core.telegram.org/bots/api#sendvideonote)). В базе игроков сохраняются метаданные. Миграция схемы PostgreSQL не требуется.

## Защита от повторов

- Журнал `video-delivery-*.json` в `RUNTIME_STATE_DIRECTORY` (по умолчанию `storage/runtime`) резервирует отправку до обращения к Telegram и защищён отдельной межпроцессной блокировкой.
- Замена кружка и перезапуск не вызывают повторную отправку пользователю за тот же тур.
- При явном отказе Telegram 429/5xx попытка возможна после указанной паузы. Для постоянных отказов, например 403, автоматических повторов нет.
- Если соединение оборвалось и результат неизвестен, повтор не выполняется: Telegram мог уже принять сообщение. Состояние `uncertain` и лог `player_video_delivery_uncertain` требуют ручной проверки.
- Авария после резервирования оставляет состояние `attempting`: оно также не повторяется автоматически. Приоритет — не отправить два кружка; в такой ситуации доставка не гарантируется.
- Не удаляйте журнал отправок. Все процессы должны использовать одну директорию состояния; включите её в резервные копии.

## Развёртывание

```bash
git pull && npm ci && npm run check && pm2 restart avto-fantasy --update-env
```

Дополнительный cron для кружков не требуется. `PLAYER_VIDEO_NOTIFICATIONS_ENABLED=false` отключает встроенный планировщик, но не ручной запуск существующего worker.
Админский тест не запускает массовую рассылку. Реальную доставку в Telegram проверяют после загрузки настоящего кружка; автоматические тесты используют подставной Telegram-клиент.
Проверки: `npm run test:videos` и `npm run check`.
